# 写作日历独立范围架构

状态：已实现，待人工验收
日期：2026-08-30

## 理解摘要

- 写作日历是可单独安装、单独工作的统计插件。
- 它需要采用与排版插件相近的“按规则筛选文件”思路，但规则由日历自己维护。
- 用户可以为统计工作区或命名项目分别配置文件夹、标签、排除文件夹、排除标签、扩展名、文件名与 Properties 条件。
- 统计工作区是日历自己的保留范围（ID 为 `workspace`）；未保存规则时等同全部写作，保存后与项目版本一起同步。
- 高级筛选是内置、类 Dataview 的小型表达式：可用 `AND`、`OR`、`NOT`、括号以及 `folder()`、`tag()`、`extension()`、`filename()`、`property()`；它不加载或要求安装 Dataview。
- 日历不得读取、订阅、导入或跟随 Chinese Writing Layout 的自动套用规则。
- 未来整合式工作台可以读取各插件公开接口，把它们协调到同一层数据或规则；当前两个插件不互相调用。
- 同步仍只通过仓库内的 `写作日历数据/` 完成，适配 Remotely Save 等文件同步工具。

## 假设与非功能要求

- 标签从 Obsidian 元数据扫描得到；`#标签` 与 `标签` 等价，比较不区分大小写，层级标签精确匹配。
- 同一类别的包含规则为“任一命中”，不同类别之间为“同时满足”；排除文件夹和排除标签优先。
- 普通条件与高级筛选之间为“同时满足”；表达式保存时校验，运行时缓存解析结果。无效表达式在遗留同步数据中会安全地匹配失败，而不会扩大统计范围。
- 项目范围变更会按当前规则重新归集已记录的历史活动；已删除文件使用索引中保留的最后标签快照。
- 索引只保存路径、聚合字数、标签与必要 Properties，不保存正文；范围更新不会改写历史 JSONL 账本。
- 扫描复用 Obsidian 的元数据缓存，正常规模仓库按批异步执行，不依赖网络服务。

## 决策日志

| 决策 | 备选 | 结论与原因 |
| --- | --- | --- |
| 规则来源 | 读取排版插件 / 日历自行维护 | 日历自行维护，避免安装顺序、协议兼容与统计归属被排版规则改变。 |
| 标签表达 | Properties 中的通用 `tags` / 一等标签条件 | 使用一等的包含/排除标签条件，使按标签统计可见、可编辑、可解释。 |
| 跨模块整合 | 现在直接耦合 / 未来工作台调用接口 | 保留版本化 `scopes` 接口；当前不运行跨插件调用。 |
| 历史数据 | 改写事件 / 当前规则重新归集 | 不改写账本，仪表盘使用当前项目规则归集，保持同步安全。 |
| 旧的 `workspaceFolders` 回退 | 保留 / 同步工作区 | 使用可编辑、可同步的 `workspace` 范围取代旧设置字段，避免隐式全局范围与项目规则冲突。 |

## 当前接口边界

Writing Calendar 在全局写作工具注册表中发布自身的版本化范围接口：

```ts
interface WritingCalendarScopeRulesApi {
  protocolVersion: 1;
  getDefinitions(): readonly ProjectDefinition[];
  saveDefinition(definition: ProjectDefinition): Promise<void>;
}
```

它只暴露日历自身的数据。未来工作台可以同时读取日历和排版插件各自公开的接口，并在工作台层决定是否建立共用规则；任何一边插件未安装时，另一边仍完整工作。

`getDefinitions()` 始终包含日历自己的统计工作区。工作台若要更新它，只需以 `id: "workspace"` 调用 `saveDefinition()`；该操作会写入日历自己的版本化同步数据，不会写入或读取 Layout 的设置。

## 明确不做

- 不读取另一个插件的 `data.json`、自动套用规则或私有状态。
- 不在日历设置页提供“打开排版插件设置”的入口。
- 不把两个插件合并为一个插件，也不新增强制共享 JSON 文件。
- 不把统计规则转换成排版行为，或把排版规则转换成日历项目。
